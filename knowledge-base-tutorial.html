02 / 目录结构

知识库长什么样？

一个清晰的目录是一切的基础。六层分离，各司其职。

knowledge-base/ 📋 index.json ← 全局索引 ⚙️ config.json ← 知识库配置 sources/ ← 原始文档（只读） 交通流预测综述.pdf 行业报告-2026.docx 技术标准-GB39786.txt markdown/ ← 转换后的 MD 交通流预测综述.md 行业报告-2026.md 技术标准-GB39786.md summaries/ ← 摘要 _all_summaries.md ← 汇总 metadata/ ← 元数据 交通流预测综述.json 行业报告-2026.json images/ ← OCR / 提取图片 交通流预测综述_fig1.png scripts/ ← 自动化脚本 convert.py index_gen.py search.py

sources/ 原始文档

只读，永不修改。所有溯源最终指向这里的原始文件。

markdown/ 转换结果

统一格式，方便 grep/read 检索。文件名与 sources/ 一一对应。

metadata/ 元数据

每篇文档一份 JSON：来源、页数、章节结构、关键词、转换时间。

summaries/ 摘要

快速预览相关性。_all_summaries.md 汇总所有文档摘要。

images/ 图片

从文档中提取的图片、OCR 结果。markdown/ 中用相对路径引用。

一键创建目录结构 · PowerShell
$base = "D:\knowledge-base" $dirs = @("sources", "markdown", "summaries", "metadata", "images", "scripts") foreach ($d in $dirs) { New-Item -ItemType Directory -Path "$base\$d" -Force }
03 / 转换流水线

把一切变成 Markdown

不同格式需要不同的转换策略，但输出统一为结构化的 .md 文件。

📕

PDF → MD

文字型 PDF 用 pandoc 或 pdf skill。扫描版需先 OCR（Tesseract）。表格用 pdfplumber 专门提取。

📄

DOCX → MD

pandoc 是首选工具，保留标题层级、表格、图片引用。或用 opencode 的 docx skill 直接读取。

📃

TXT → MD

最简单。自动检测编码（UTF-8/GBK），添加标题和分段标记即可。

metadata/交通流预测综述.json · 示例
{ "source_file": "sources/交通流预测综述.pdf", "title": "基于机器学习的交通流预测方法综述", "converted_at": "2026-06-04T14:30:00", "format": "pdf", "page_count": 12, "md_file": "markdown/交通流预测综述.md", "hash": "a1b2c3d4...", "sections": [ { "title": "摘要", "page": 1, "line_start": 1, "line_end": 28 }, { "title": "2. 方法论", "page": 3, "line_start": 82, "line_end": 165 } ], "keywords": ["交通流","LSTM","图神经网络"], "quality": "auto" }
转换命令 · 实操
# PDF 转 Markdown（保留结构） pandoc "sources/论文.pdf" -f pdf -t markdown \ --wrap=none -o "markdown/论文.md" # DOCX 转 Markdown（保留图片引用） pandoc "sources/报告.docx" -f docx -t markdown \ --extract-media="./images" \ -o "markdown/报告.md" # TXT 编码转换（GBK → UTF-8） python scripts/convert.py \ --input "sources/标准.txt" \ --output "markdown/标准.md" \ --detect-encoding # 或直接用 opencode 交互 → 请把 sources/论文.pdf 转为 markdown → opencode 会调用 pdf skill 自动完成

⚠️ 转换质量检查清单

  • 页数是否对应？转换后段落数与原文件对比
  • 表格结构是否完整？打开 MD 检查 Table 语法
  • 公式是否保留？LaTeX 公式应保留为 $...$ 或 $$...$$
  • 图片是否提取？检查 images/ 目录和 MD 中的引用路径
  • 中文是否乱码？打开 MD 文件目视检查前几段
04 / 索引生成

给知识库建一张"目录卡"

index.json 是整个系统的核心——它记录每篇文档的位置、结构、关键词，让检索做到秒级定位。

index.json · 全局索引
{ "version": "1.0", "updated_at": "2026-06-04T15:00:00", "total_documents": 3, "documents": [ { "id": "doc_001", "title": "基于机器学习的交通流预测方法综述", "source": "sources/交通流预测综述.pdf", "markdown": "markdown/交通流预测综述.md", "metadata": "metadata/交通流预测综述.json", "summary": "本文系统综述了基于机器学习的...", "keywords": ["交通流", "LSTM", "GNN", "预测"], "sections": ["摘要", "1.引言", "2.方法", "3.实验", "4.结论"] }, { "id": "doc_002", "title": "行业报告-2026", "source": "sources/行业报告-2026.docx", "markdown": "markdown/行业报告-2026.md", "keywords": ["市场分析", "趋势"], "sections": ["概述", "数据统计", "结论建议"] } ] }
📊

索引包含什么

文档 ID、标题、源文件路径、MD 文件路径、关键词、章节列表、摘要预览。足以支撑目录导航和关键词初筛。

⚙️

如何生成

扫描 markdown/ 目录，提取每个 MD 文件的 # 标题结构，结合 metadata/*.json 生成。用脚本自动化，也可让 opencode 执行。

summaries/_all_summaries.md · 摘要汇总
# 知识库摘要汇总 > 自动生成，最后更新：2026-06-04 --- ## doc_001 · 基于机器学习的交通流预测方法综述 - 来源：sources/交通流预测综述.pdf（12 页） - 摘要：本文系统综述了基于机器学习的交通流预测方法，涵盖 LSTM、GRU、GCN 等模型，在三个公开数据集上进行了对比实验。 - 关键词：交通流, LSTM, 图神经网络, 预测 ## doc_002 · 行业报告-2026 - 来源：sources/行业报告-2026.docx（45 页） - 摘要：2026 年行业市场分析报告，包含市场规模、竞争格局... - 关键词：市场分析, 趋势, 统计数据
05 / 四层检索策略

从宽到窄，层层逼近

不一次读全文，而是逐层缩小范围——这是控制上下文消耗的核心。

L1

索引导航

在 index.json 中匹配标题 / 关键词，找到相关文档 ID 和章节位置。

秒级 · O(1)
L2

摘要预览

读取 summaries/_all_summaries.md，判断文档是否与问题相关，排除无关内容。

秒级 · 少量 Token
L3

正则精准定位

在目标 MD 文件中用 grep/正则搜索关键词，定位到具体行号范围。

毫秒级 · 精确
L4

精确读取

按行号范围 read 目标段落，只返回命中内容 + 来源标注。

06 / 来源溯源

每条结果都要"有据可查"

行业场景下，"AI 说的"不算数，"文档写的"才算。每条返回结果必须携带来源标注。

📆 来源标注
本文采用 LSTM（长短期记忆网络）对城市主干道的交通流量进行预测，实验结果表明，在三个公开数据集（PeMSD4、PeMSD8、PeMSD7(M)）上，LSTM 模型在 MAE 和 RMSE 指标上均优于传统 ARIMA 方法。
📄 来源：交通流预测综述.pdf 📑 第 3 页 · 2.方法论 📝 markdown/交通流预测综述.md:89-115 ✅ 质量：已验证

溯源三要素

1. 原始文件路径 → sources/xxx.pdf
2. 页码/章节 → 第 X 页「章节名」
3. 行号定位 → markdown/xxx.md:行号范围

溯源规范

❌ 禁止 AI 改写原文后不加标注
❌ 禁止只给摘要不给原文引用
✅ 必须返回原文段落 + 三要素标注
✅ 可选附加 AI 总结，但需明确区分

💡 Hash 去重机制

每个文件转换前计算 SHA-256 Hash，与 metadata/*.json 中的 hash 字段比对。
Hash 一致 = 已转换过，跳过。Hash 变化 = 文件被修改，重新转换。
这保证了：同文件不重复转换，修改过的文件能被检测到。

09 / Phase 2 预告

当关键词匹配不够用时

Phase 2 将引入语义检索（RAG），与 Phase 1 的精确匹配形成互补。

对比维度Phase 1（当前）Phase 2（扩展）
检索方式关键词 + 正则精确匹配向量语义检索 + 正则验证
理解能力"交通流"只能匹配这三个字"交通流"也能找到"车流"、"拥堵预测"
精确度字符级精确，不会错配语义级近似，可能召回非目标
额外依赖无Embedding 模型 + ChromaDB
成本零本地免费 或 API 按量付费
适用场景标准号、术语、公式、参数"帮我找和这段话意思相近的内容"
推荐策略单独使用与 Phase 1 混合使用
🧨

Embedding 模型

推荐 bge-small-zh（本地 CPU 可跑）或智谱 Embedding API。负责把文字变成向量。

💾

ChromaDB

轻量级向量数据库，纯 Python，零配置。存储文档向量，支持相似度查询。

🔄

混合检索

RAG 语义召回 Top-10 → grep 精确验证 → 只返回经双重确认的结果。兼得广度与精度。

💡 建议

先用 Phase 1 跑通全流程，积累 50+ 篇文档后，如果你发现"关键词匹配找不到想要的内容"，再启动 Phase 2。届时所有 MD 文件已就绪，只需额外做 Embedding 即可，迁移成本几乎为零。
